# EnderWriter 末影箱 · 结构与原理说明

> 生成时间：2026-10-17
> 说明对象：当前本机已部署的实际状态（非规范设想）

---

## 一、它解决什么问题

长篇小说 AI 写作的真正瓶颈不是单章质量，而是**跨章一致性**：

- 角色第 30 章晋升斗帝，第 42 章有人还说他斗气三段
- 第 12 章埋的伏笔，第 200 章没回收，也没人记得
- 同一角色称呼从「师姐」漂移到「阿姐」

百万字塞不进任何模型的上下文窗口。所以需要**外置的结构化长期记忆 + 按需检索**。

**非目标**：不做纯上下文压缩；不把整本书塞进窗口；不靠模型"硬记"。

## 三、两层记忆（核心设计）

### 3.1 为什么要分两层

两类信息天然不同：

| 类型 | 例子 | 归属 |
|---|---|---|
| **作品细节** | 张三是青霄剑宗弟子、断魂钉是宗门凭物 | 属于某一部作品，跟作品走 |
| **文学经验** | 前三章必须建立处境、单章不超 2 条伏笔 | 属于作者本人，跨所有作品通用 |

### 3.2 物理分库

```
enderwriter/memory/
  works/
    对话-99017a6c-cc9767.db   ← 某个对话的独立记忆
    示例小说-5b512f.db            ← 作品《示例小说》的记忆
    示例卷-a5d0f9.db          ← 作品《示例卷》的记忆
  global.db                   ← 跨对话共享的文学经验
```

**一个作品一个 SQLite 文件**，互不干扰。删掉某个文件就等于清空那部作品。

### 3.3 自动路由

写入时按 `layer` 决定去哪：

| layer | 去哪 |
|---|---|
| `character` 人物 | 作品库 |
| `world` 世界 | 作品库 |
| `timeline` 时间线 | 作品库 |
| `foreshadowing` 伏笔 | 作品库 |
| `item` 物品 | 作品库 |
| **`style` 风格** | **全局库** |

也可以用 `scope` 参数强制指定。

## 四、会话隔离（默认按对话）

### 4.1 规则

- **默认**：每个对话一套独立记忆，互不可见
- **显式指定**：说"用作品《示例小说》"，那个对话就接入共享库

### 4.2 命名

对话专属库的命名：`对话-<会话ID后8位>`

```
session-f9e25f1f-2111-4142-a784-5b9199017a6c
  → 取末尾数字字母 99017a6c
  → 作品名「对话-99017a6c」
  → 文件 对话-99017a6c-cc9767.db
```

### 4.3 会话 ID 从哪来

```
工具调用 → ctx.agent.id（当次调用的会话）
面板     → Host 记录的「最近活跃会话」
```

**关键点：不做任何模块级缓存。** Host 进程被所有会话共享，缓存会导致跨对话串场——这是之前踩过的坑。

### 4.4 会话 ID 缺失时

不会回退到 `process.env.DSH_SESSION_ID`（那是进程启动时的固定值，所有会话都一样）。没拿到就当作无会话，只用全局库。

## 五、末影箱内部结构

### 5.1 数据库表（9 张）

| 表 | 作用 |
|---|---|
| `records` | 主表：`(layer, entity)` 主键，存 content / version / embedding |
| `history` | 版本历史，**只追加不覆盖** |
| `terms` | 关键词倒排索引 |
| `aliases` | 称呼映射（别名 → 标准名） |
| `edges` | 关系图边 |
| `state` | 实体 × 键 → 当前值 + 所属章节 |
| `chapters` | 章节正文 |
| `meta` | 元信息（schema 版本等） |
| `sqlite_sequence` | SQLite 内部 |

### 5.2 七个格子

`character` 人物 / `world` 世界 / `timeline` 时间线 / `foreshadowing` 伏笔 / `item` 物品 / `style` 风格 / `alias` 称呼

### 5.3 版本语义

每条记录带 `version` 和 `last_updated`。每次写入 version+1，旧值进 `history` 表。

```sql
-- 第 1 次写
张三 v1: "青霄剑宗弟子"
-- 第 2 次写
张三 v2: "晋升斗帝"
-- history 表里两条都在
```

这是「按章回滚」的数据基础。

### 5.4 伏笔状态机

```
planted（已埋）
   ↓ reinforce
reinforced（已强化）
   ↓ resolve          ↓ abandon
resolved（已回收）  abandoned（已废弃）
```

## 六、四类索引

| 索引 | 实现 | 用途 |
|---|---|---|
| **关键词倒排** | `terms` 表 | 中文双字组切分，权重：实体 3.0 / 标题 2.0 / 正文 1.0 + IDF |
| **向量** | `records.embedding` BLOB | 256 维，numpy 暴力余弦 |
| **图** | `edges` 表 | 关系边，支持多跳扩展 |
| **状态** | `state` 表 | 实体 × 键的当前值 |

### 中文分词方案

SQLite FTS5 无法切中文，`jieba` 属重依赖，所以用**确定性 CJK 双字组**：

```
"萧炎走进了宗门"
  → 萧炎、炎走、走进、进宗、宗门
  → 加上整串（≤4字时）
```

索引侧与查询侧共用同一个 `analyze()`，保证一致。

## 七、检索流程

```
1. 实体归一化    别名 → 标准名（称呼格）
       ↓
2. 多通道召回    关键词 / 向量 / 图 / 实体精确命中 / 2跳弱相关
       ↓
3. 三档分层      high（多通道命中，给全文）
                medium（单通道，给摘要）
                low（弱相关，抽样 1-2 条）
       ↓
4. 预算裁剪      单次 ≤ 800 token
                档位预算 50% / 35% / 15%
       ↓
5. 结构化返回    {high, medium, low, total_tokens}
```

### 两个优化

- **已在上下文中的实体**返回「已在上下文」，只按 4 token 计费，不重复占预算
- **low 档轮转**：同一写作周期内不重复抽同一条

## 八、P0-P4 上下文预算

章节上下文总量 = 模型窗口的 **70%**

| 优先级 | 内容 | 占比 |
|---|---|---|
| P0 | 全局大纲、当前细纲、核心人物卡、待处理伏笔 | 30% |
| P1 | 高相关预检索 | 30% |
| P2 | 近期正文（最近 1-2 章） | 20% |
| P3 | 中相关结果、次要角色与地点 | 15% |
| P4 | 探索样本、风格样本 | 5% |

每段用 `clip_tokens` 严格截断，总量有硬断言。

### 动态追加

生成过程中监听文本流，识别新出现的实体名，后台增量检索并注入。异常一律静默，不打断生成。

---

## 九、写后处理

### 9.1 回写

每章写完，把变化写回末影箱：人物状态、物品归属、时间线、伏笔状态。

### 9.2 四类矛盾检测

| 类型 | 判据 |
|---|---|
| 死而复生 | `alive=False` 却在 active_characters 出现 |
| 时间倒错 | 新事件章号早于该角色状态最后更新章 |
| 能力违规 | 境界回退等与已记录状态冲突 |
| 称呼漂移 | 正文别称与称呼格登记不一致 |

### 9.3 伏笔巡检

- **超期**：`当前章 > 计划回收章 + 宽限期` → 告警 + 生成回收建议
- **陈旧**：`planted` 且超 30 章未强化 → 标记 `abandon_candidate`

## 十四、一次完整调用发生了什么

以「查一下张三的设定」为例：

```
1. 你说："查一下张三的设定"
2. AI 决定调用 enderwriter_recall({entities:["张三"], budget:800})
3. Host 插件 index.js:
     ctx.agent.id → "session-f9e2...7a6c"
     拼请求 {"op":"recall","entities":["张三"],"session_id":"...","budget":800}
4. spawn Python: python -m enderwriter.bridge --stdin
5. bridge.py op_recall:
     memory.resolve_work() → "对话-99017a6c"
     作品库路径 → memory/works/对话-99017a6c-cc9767.db
     keep.search() → 三档结果
     全局库也查一遍
6. 返回 {scopes:{work:{...}, global:{...}}, total_tokens:32}
7. Host 渲染成文本给 AI
8. AI 回答你
```

### 开发中修掉的实际缺陷

1. **伏笔状态落盘丢失** —— `data.update(extra)` 用旧快照覆盖了新值
2. **P1/P3 上下文为空** —— 细纲读取只认嵌套结构
3. **`entries` 凭空造数据** —— 分支条件写错，掉进临时库并自动灌种子
4. **会话串场** —— 会话 ID 用了模块级共享变量
5. **插件文件编码损坏** —— PowerShell 改中文源文件导致，已改为用 write 工具
6. **面板样式无动画** —— 全行内 style，写不了 hover/keyframes
7. **自建 HTTP 路由 401** —— 位于连接鉴权之外，改用官方 RPC

## 十七、已知限制

| 项 | 说明 |
|---|---|
| 面板会话定位 | 面板是 root 作用域，只能显示「最近活跃会话」的记忆，无法切换到指定对话 |
| 面板开关 | `setEnabled` 只影响显示，不真正停止记忆写入（真正关闭需改 `cordis.patch.yml` 的 `enabled: false`） |
| Ollama 未装 | 本机网络受限，实际用 llama.cpp 路线 |
| 分库命名 | 对话 ID 取后 8 位，理论上极小概率碰撞 |
