# 05 · 技术护栏

把「事故复盘」变成「可机械判定的规则」。

---

## 为什么需要这一层

技术库原本只存**案例叙述**（"当时发生了什么"）。三个问题：

1. **只在人主动去查时有效** —— 而事故恰恰发生在"不知道自己不知道"的时候
2. **叙述要读完 800 字才拿到要点** —— 实战中不会读
3. **通用教训被项目细节淹没** —— "dcs逆向 v1.1.2"这类，换个项目就以为无关

**断言**回答的是另一个问题："下次别再犯什么"。

```
案例（叙述）        断言（护栏）
「当时我们遇到…」   rule        重载 operator== 里不许用 a == null 判空
「因为…所以…」     detect_all  ["operator ==", "== null"]
「后来改成…」      detect_not  ["ReferenceEquals"]
                    fix         改用 ReferenceEquals(a, null)
                    consequence 每次比较 71ms，30 实例掉到 0.3 FPS
```

**左边是知识，右边是护栏。** 技术库现在两者都有。

---

## 两种触发方式

### 1. 代码特征（写的时候抓）

```python
{
  "id": "unity-operator-eq-null-recursion",
  "rule": "重载了 operator== 的类，运算符体内不得用 a == null 判空",
  "detect_all": ["operator ==", "== null"],     # 全部出现才命中
  "detect_not": ["ReferenceEquals"],            # 出现这个说明已写对
  "fix": "判空改用 ReferenceEquals(a, null)",
  "consequence": "无限递归→栈溢出被 catch 吞掉，每次 71ms",
  "severity": "high"
}
```

判定：

```python
if any(t in text for t in detect_not):   return None    # 已写对，不吵
if not all(t in text for t in detect_all): return None  # 条件不全
return hit
```

### 2. 任务意图（动手之前抓）

```python
{
  "id": "unity-writeback-field-order",
  "rule": "回写 DLL 前必须逐类型比对序列化字段声明顺序，必须 0 差异",
  "when": ["回写 DLL", "Assembly-CSharp"],      # 任务描述里出现就触发
  "detect_all": [],                             # 没有代码条件
  "fix": "用 Mono.Cecil 导出实例字段声明顺序，与原 DLL 对比",
  "consequence": "顺序变了会报 level0 corrupted 并崩溃"
}
```

**为什么必须有这个**：像"回写前必须比对字段顺序"这种流程性教训，源码里没有对应特征，只能靠"你正要干这件事"来触发。

## 校验器：挡住会误报的断言

这是整个系统最关键的一段。

### 模型会产出什么废品

用模型从案例抽断言时，实测会生成两类：

```
["operator =="]                条件太宽，任何重载都报
["Update", "snInfo =="]        绑死变量名，换项目就失效
```

**这两类都会让断言持续误报 → 被无视 → 整个功能被关掉。**

### 确定性校验规则

```python
def validate(rule, detect_all, when=(), allow_single=False):
    # 1. rule 不能为空
    # 2. detect_all 与 when 至少要有一个
    # 3. 靠代码特征触发时，至少 2 个条件
    # 4. 拒绝通用词
    # 5. 拒绝太短的条件（< 3 字符）
    # 6. when 关键词至少 2 字符
```

### 通用词黑名单

```python
_GENERIC_TOKENS = {
    "void update", "void start", "void awake",
    "public class", "private void", "using system", "using unityengine",
    "for (", "while (", "if (", "return ", "var ", "int ", "string ",
    "catch (", "try {", "else {", "{", "}", "()", ";",
}
```

这些在普通项目里到处都有，作为匹配条件等于"永远命中"。

### 单条件的例外

```python
save(chest, "dnspy-residual", "出现 >g__ 说明是编译器生成的局部函数",
     detect_all=[">g__"], allow_single=True)
```

`>g__` 只出现在 C# 编译器生成的局部函数名里，本身就是唯一信号。

## 使用

### 检查代码

```python
from enderwriter.guard import guard

hits = guard(chest, code_text)
```

实际输出：

```

[高] unity-operator-eq-null-recursion（第 2 行）
  规则：重载了 operator== 的类，运算符体内不得用 a == null 判空
  命中：operator == + == null
  后果：无限递归 → 栈溢出 → 被同函数的 catch 吞掉，无任何报错；
        每个调用点约 71ms，30~80 个实例在 Update 里即掉到 0.3 FPS
  修法：判空改用 ReferenceEquals(a, null) 或 (object)a == null
```

### 已写对时不吵

```python

bool operator ==(A a, A b) {
    return ReferenceEquals(a, null) || ReferenceEquals(b, null);
}
"""
guard(chest, code)
# → []   detect_not 命中，不报警
```

## 误报反馈闭环

### 问题

断言会误判。但如果误报无处消化，报多了用户只能关掉整个功能。

### 解决

```python
enderwriter_feedback(kind="assertion",
                     ref="unity-operator-eq-null-recursion",
                     verdict="fp",           # fp=误报 / tp=真问题
                     note="这次是安全的")
```

### 自动降级

```python
stats = chest.feedback_stats("assertion")
# {"assertion:unity-operator-eq-null": {"fp":2, "tp":0, "total":2, "fp_rate":1.0}}

# 护栏输出时
if total >= 2 and fp_rate >= 0.5:
    rendered += "\n⚠ 其中 X 历史上多次被判为误报，命中仅供参考。"
```

输出：

```
[高] unity-operator-eq-null-recursion（第 1 行）
  ...
⚠ 其中 unity-operator-eq-null-recursion 历史上多次被判为误报，命中仅供参考。
```

**降级条件**：累计 ≥2 次且误报率 ≥50%。单次误报不轻易否定一条断言。

## 从案例到断言的流程

```
1. 踩了坑 → 写成案例（叙述）
   enderwriter_remember(layer="style", entity="unity性能杀手:operator==自递归")

2. 从案例提炼断言
   enderwriter_assert(
     id="unity-operator-eq-null-recursion",
     rule="重载 operator== 里不得用 == null 判空",
     detect_all=["operator ==", "== null"],
     detect_not=["ReferenceEquals"],
     cases=["unity性能杀手:operator==自递归"])

3. 以后写代码时自动命中
```

**关键**：第 2 步是人工的，不是自动的。

- 自动抽取会产出废品（见上文校验器）
- 而且**不是所有教训都能变成断言**

### 不能变成断言的教训

| 教训 | 为什么不能 |
|---|---|
| 「用时间窗口探针排查」 | 是**方法**，源码里没特征 |
| 「字段顺序必须对齐」 | 是**流程**，只能靠 when 触发 |
| 「ldc.r4 必须按字节核对」 | 是**操作**，同上 |

前两个用 `when` 覆盖；纯粹的排查方法论留在案例正文里。

**硬做成代码断言只会误报，而误报会让人关掉整个功能。**

## 与关系抽取的配合

断言和案例之间用 `cases` 字段关联：

```python
{
  "id": "unity-operator-eq-null-recursion",
  "cases": ["unity性能杀手:operator==自递归被catch吞掉"]
}
```

这样从护栏命中 → 可以追溯到原始案例 → 看完整的事故经过。

## 一句话总结

**报告需要人主动去读，护栏不需要。**

技术库的价值不在于"存得多好"，而在于"能不能在你不查的时候也出现"。

- 代码特征 → 写的时候自动命中
- 任务意图 → 动手之前自动提示

两者都做到了，才算真的"减少下一个产物犯错"。
