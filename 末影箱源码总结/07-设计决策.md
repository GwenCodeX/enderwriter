# 07 · 设计决策

每个决策都记录"为什么"，包括被否定的方案。

---

## 决策一览

| # | 决策 | 替代方案 | 为什么否掉替代方案 |
|---|---|---|---|
| 1 | 一致性检查用确定性规则 | 本地 3B 模型审查 | 误报率 >80% |
| 2 | 版本历史追加式 | 直接覆盖 | "AI 可放心覆写"的前提 |
| 3 | 废止只认显式标记 | 从正文关键词自动识别 | 实测 6 条全是误判 |
| 4 | 断言校验器严格 | 来者不拒 | 误报断言会让功能被关掉 |
| 5 | 弱边直接丢弃 | 全部保留 | 多跳检索被噪声稀释 |
| 6 | 整理只报告不合并 | 自动合并 | 吃掉重要差异无法恢复 |
| 7 | 弹层全部改为原地展开 | 提高弹层 z-index | 宿主环境不可控 |
| 8 | 面板编辑走版本 | 直接改库 | 改错要能回去 |
| 9 | usage 独立成表 | 塞进 records.data | 会推高版本号、撑爆 history |
| 10 | 导入默认只预演 | 直接写入 | 分节和判层都可能出错 |

## 1 · 一致性检查为什么不用模型

最初设计是让 Qwen（3B）当审查员。实测：

```
输入：事实「主角甲左手刀伤缠绷带」+ 正文「主角甲右手握剑」
输出：{"violated": true, "reason": "右手握剑与左手刀伤冲突"}
       ← 这条其实是**误报**：左右手不冲突

输入：事实「主角甲境界=白牌」+ 正文「主角甲双手握剑」
输出：{"violated": true, "reason": "正文没有提及境界"}
       ← 把「没提到」当「违反」
```

**误报率超过 80%**，逐条二分类也治不了——3B 分不清「没提到」和「提到了但冲突」。

所以改成确定性规则。代价是没有语义理解，只能覆盖能用规则表达的冲突类型（R1-R5）。

**附带发现**：R1「已死亡角色行动」这条，必须读完整段原文而不是模型摘要，才能识别「缠绷带」这种细节——规则引擎恰恰相反，字面匹配从不漏细节。

## 2 · 版本历史为什么追加式

```
upsert → version+1 → 旧内容 INSERT INTO history
```

这带来三个能力：

1. **AI 可以放心覆写**——旧内容永不丢失
2. **回滚本身可再回滚**——把 v1 写回成 v4，v1~v3 全保留
3. **「上次改了什么」可查**——这是设定集最常被问的问题之一

如果直接覆盖，第 2、3 条都不存在，覆写等于永久丢失。

## 3 · 废止为什么只认显式标记

第一版用正文关键词识别：「已废止 / 已作废 / 已取消」等。

实测在涟城库上**6 条全是误判**：

```
战力牌级表     「字母记法…已废止，唯一有效的体系就是本条」  ← 现行版
涟城原型大连   「此前「涟城临江」的写法错误，已废止」      ← 现行版
白露          「档案曾使用字母记法…该记法现已废止」        ← 现行版
```

**规律**：一条记录说「X 已废止」时，它通常正是**取代 X 的那条**。

结论：猜不如让人声明。现在废止只有两个途径：

```python
data["superseded"] = True        # 手动标记
data["status"] = "superseded"    # 或状态字段
```

检索时正文不返回（避免新旧口径冲突），但实体名会报出来——"这条说法已作废"本身就是结论。

## 4 · 断言校验为什么严格

用模型抽断言，会产出两类废品：

```
["operator =="]           条件太宽，任何重载都报
["Update", "snInfo =="]   绑死变量名，换个项目失效
```

这两类的下场完全一样：**持续误报 → 被无视 → 功能被关掉。**

一条永远误报的断言，比没有断言更糟。

所以校验器挡在入库之前：

```python
# 至少 2 个条件（除非 allow_single，用于 >g__ 这种唯一信号）
# 拒绝通用词（void Update / for ( / if ( ...）
# 拒绝太短的条件（< 3 字符）
```

宁可入库少，也不能让会误报的混进去。

**附带**：内置 9 条断言全部写好了对应的校验测试，任何一条不合法都会被测试抓出来。

## 5 · 关系抽取为什么丢弃弱边

自动抽关系的通病：

```
候选 25 条 → 强边 11 条 → 丢弃弱边 14 条
```

如果 25 条全保留，多跳检索会把「顺带提了一句」的也拉进来。检索结果的信噪比下降，**比不建边更差**。

强边标准：

- 被提到 ≥ 2 次，**或**
- 出现在正文开头 80 字内（主题级关系）

另外每个源实体最多保留 12 条出边，防止"什么都有关"的枢纽节点。

## 6 · 整理为什么不自动合并

涟城库里有明显重复：

```
残兽本质-现象而非兽      1504 字
敌我同源整合模型         1528 字
敌我同源与代打状态       1066 字   ← 前两条高度重叠
```

自动合并的风险：吃掉重要差异，而且**几个月后才可能被发现**。

所以 `organize()` 只做三件事：

1. **指出**哪些高度重复（Jaccard ≥ 0.55，带相似度分数）
2. **指出**孤立条目、已废止、从未使用
3. 导出时按结构组织

合并必须人工确认；即使合并，也走版本号（旧版全部保留，可回看）。

## 7 · 弹层为什么全部改成原地展开

这个折腾了最多轮次。

### 现象

点「编辑」「历史」「删除」，面板毫无反应。

### 排查过程（走了三轮弯路）

```
第一轮：以为是 props/闭包问题 → 改成 props 传递 → 没解决
第二轮：以为是缺 HTTP 端点 → 补上端点 → 没解决
第三轮：渲染测试全过、DOM 树里有节点 → 那只能是"渲染了但看不见"
```

### 根因

```css
.ew-scrim {
  position: fixed;
  z-index: 70;        ← 被宿主 UI 盖住
}
```

`position: fixed` + 自建 z-index 在宿主容器里不可靠。提到 `2147483000` 也不稳定（取决于宿主的层叠上下文）。

### 解决

不再和遮罩纠缠。编辑、历史、删除全部改成**条目行内原地展开**：

```
点击的条目
└── 直接撑开内容（文本框 / 版本列表 / 确认块）
```

走正常文档流，不可能被盖住。

**教训**：DOM 测试验证不了"能不能看见"。渲染对了不等于显示了。

## 8 · 面板编辑为什么走版本

面板上的「编辑」保存时：

```python
chest.upsert(...)   # version+1，旧内容进 history
```

不是直接改库。改错了随时「历史」里回滚。原文永远不会被覆盖。

这和 AI 覆写用的是同一条路径——人改的和 AI 改的，版本历史在一起。

## 9 · usage 为什么独立成表

第一版打算塞进 `records.data`。两个问题：

1. `data` 参与版本管理，每次命中 bump version 会把 `history` 撑爆
2. 使用记录是"关于记忆的元数据"，与内容本身的生命周期不同

独立成 `usage` 表后：命中只改这张表，records/history 完全不动。

**语义**：检索命中 = 已回收归档。但**只标记，不删除**——设定集里的条目可能在几百章后被再次引用。

## 10 · 导入为什么默认只预演

导入是有损的：分节方式、图层判断都可能出错。而写进库的东西会参与检索、影响写作。

```
60,183 字设定稿 → 预演：16 条、28,902 字、跳过 4 条
用户看清单 → 确认 → dry_run=false → 才写库
```

预演清单包括：每条叫什么、判成哪层、多少字、前 60 字预览。跳过的也会说明理由（如「逐章细纲——写作产物」）。

## 附：检索预算的两个关键参数

### medium 档可读下限

```
之前：22 条候选 / 280 预算 → 每条 12 tokens ≈ 8 个汉字
      条目名本身 10~15 字，摘要比标题还短，等于没有

现在：每条至少 80 tokens（≈55 汉字）
      预算不够就少返回几条
```

**三条看得懂的，比二十二条看不懂的有用。**

### 上下文总预算

```
P0 细纲      30%
P1 相关设定  30%
P2 前文摘要  20%
P3 风格样本  15%
P4 兜底       5%
─────────────────
合计 = 窗口的 70%，留 30% 给生成
```

P4 吸收浮点余数，保证不超窗。
